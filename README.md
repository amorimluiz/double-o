# double-o

Personal, harness-agnostic source of truth for agent-assisted development.

This repository holds my global agent configuration — instruction files, skills, engineering rules, and per-harness config — as the single canonical copy. Each machine symlinks its harness's expected paths back into this repo, so a `git pull` propagates changes to every machine automatically.

## How it works

Instead of copying files around, every harness reads through a symlink that points back here:

```
~/.config/opencode/AGENTS.md  ──symlink──▶  double-o/instructions/AGENTS.md
~/.agents/skills/             ──symlink──▶  double-o/skills/
~/.config/opencode/rules/     ──symlink──▶  double-o/rules/
```

Edit anything on one machine, commit, pull on another — the changes are already live behind the symlinks. No installer to re-run, no drift between machines.

## Repository structure

```
double-o/
├── instructions/          # Canonical agent instruction files
│   └── AGENTS.md          # Global governance (not auto-loaded from here)
├── rules/                 # Engineering standards, one topic per file
├── skills/                # Canonical skills, one folder per skill
│   ├── 00-loop/           # SDD pipeline: entry point + execution loop
│   ├── 00-prd/            # SDD pipeline: product requirements
│   ├── 00-tasks/          # SDD pipeline: task graph
│   ├── 00-techspec/       # SDD pipeline: technical design
│   └── <vendored>/        # Third-party skills (provenance in skills-lock.json)
├── harnesses/             # Per-harness config owned by this repo
│   └── opencode/
│       ├── opencode.jsonc
│       └── package.json
├── skills-lock.json       # Provenance and versions for installed skills
├── SETUP.md               # Agent-followable install instructions
└── README.md
```

External libraries (e.g. RTK) are **not vendored**. Their plugins, hooks, and instruction files are generated by the library's own installer, per harness — see [SETUP.md](SETUP.md). The repo only keeps the reference (e.g. `@RTK.md` in `AGENTS.md`), which resolves to the file the installer creates, so updating the library updates the artifact automatically.

### Why `instructions/` and not the root?

`AGENTS.md` in a repository root is auto-loaded by harnesses when working inside that repository. Keeping it under `instructions/` means it is only read where it is symlinked (the harness's global config), avoiding duplicate context.

## Setup

On a new machine, hand [`SETUP.md`](SETUP.md) to your agent. It detects the installed harnesses, creates the correct symlinks for the repo's artifacts, and runs each external library's own installer.

> [!IMPORTANT]
> The repository must live at a stable path — symlinks point to it. Moving it breaks every link.

## Managing skills

The `00-*` skills (the SDD pipeline) are authored in this repo. The rest are fetched with the [Skills CLI](https://skills.sh) and kept in `skills/` as the canonical source.

```bash
npx skills find <query>                                  # search
npx skills add <owner/repo> --skill <name> -y            # fetch a skill
npx skills update                                        # update tracked skills
```

After fetching, move the skill folder into `skills/` so it becomes part of the canonical set. `skills-lock.json` records where each skill came from.

## Adding a harness

1. Add a folder under `harnesses/<name>/` mirroring that harness's global config directory.
2. Add the harness's target paths to the table in [`SETUP.md`](SETUP.md).
3. Re-run the symlink step on each machine.

## Design principles

- **Harness-agnostic.** Nothing here assumes a specific agent. Per-harness details are isolated under `harnesses/`.
- **Single source of truth.** One canonical copy, symlinked into place. Changes propagate by `git pull`.
- **No vendoring.** Only artifacts this repo owns are tracked. Libraries are installed by their own installers; the repo references their output, never copies it.
- **No hidden context.** Auto-loaded paths stay out of the repo root, so nothing is read twice.
